Let's build this as your first complete module of OS Performance Observatory, step by step. We'll keep it beginner-friendly, but structure it like a real project so your teammates can integrate it with the analyzer and diagnosis features later.

The feature has two parts:
1. Backend collector: reads live CPU, memory, swap, and process information from the operating system.
2. Dashboard: periodically refreshes the metrics and displays charts, summary cards, and the top resource-consuming processes.
We'll use Python + psutil + Streamlit. You don't need a separate frontend or database for this feature yet.

Understand what this code is doing

CPU utilization

psutil.cpu_percent(interval=None) returns CPU utilization measured since the previous reading. The first reading can be 0.0 because there is no previous interval to compare against. Later samples are more meaningful.



RAM metrics

psutil.virtual_memory() provides total RAM, used RAM, available RAM, and utilization percentage. available is generally more useful than free for understanding how much memory can be made available without swapping.



Swap metrics

psutil.swap_memory() reports the swap capacity, usage, and percentage. High swap usage alone does not necessarily indicate an active memory bottleneck; interpret it alongside other metrics.



Top processes

Each process has a PID, name, CPU percentage, memory percentage, resident memory, and status. We sort the same process snapshot two ways to obtain the top CPU consumers and top memory consumers.



Important: Process CPU readings are also interval-based. The first reading for a process may be zero. A process can disappear between collection steps, so the code catches common process-access errors instead of crashing.

The running_process_count above counts processes reported in the running state, not every process that exists. If your evaluator means total process count instead, add a separate total count using len(psutil.pids()) and label the two values clearly.

What makes the dashboard update automatically?
This line is responsible:
@st.fragment(run_every=2)



It tells Streamlit to rerun the dashboard fragment every two seconds. On each refresh, the application collects a new snapshot, updates the metric cards and process tables, and appends a new observation to the trend chart.

We store the recent history in st.session_state, so it survives the fragment's reruns during the current session. We limit it to 60 samples to keep the dashboard lightweight.

At a two-second interval, the chart will display roughly the last two minutes of observations once it has filled up.
5. Run the application
Your folder should now look like this:
os-performance-observatory/
├── app.py
├── collector.py
├── requirements.txt
└── .venv/


Activate your environment if it isn't already active:
source .venv/bin/activate


Launch the dashboard:
streamlit run app.py


Streamlit will provide a local address, usually http://localhost:8501. Open it in your browser.

You should see live metric cards, memory information, trend charts, and the two process tables.

7. Test the dashboard under different conditions
Testing checklist
0 of 5 checked

[ ] Normal system activity

Metrics display correctly; no diagnosis is generated by this monitoring module.


[ ] CPU-intensive task

CPU utilization rises, and the process rankings update across subsequent samples.


[ ] Memory-intensive task

RAM utilization changes, and memory-heavy processes appear in the ranking.


[ ] Recovery after a task ends

New samples show the resource usage falling when the workload stops.


[ ] Process exits during sampling

The collector skips inaccessible processes and continues running.



For your first demonstration, a simple CPU-intensive task is enough. On Linux, you can use:
yes > /dev/null


This consumes CPU until you stop it with Ctrl+C. Start it in a separate terminal, observe the dashboard, then stop it and observe recovery. It may use one CPU core heavily, so the overall CPU percentage depends on the number of available cores.

Don't run multiple copies or leave the command running unnecessarily.
